# 抖音普通视频接入移动分享页 HTTP 解析

## 目标

在 `parse_video` 的本机 Docker 服务中，调用方提交小红书或抖音链接，由统一接口自动选择平台解析流程。抖音普通视频应能通过匿名 HTTP 取得可下载的 MP4 直链。

## 背景

- 统一入口已提供平台分流、鉴权、限流和缓存。当前抖音适配器通过匿名 Chromium 取得作品数据。见 `app/api/routes.py:52`、`app/parser/adapters.py:49`。
- 独立本机 Docker 已验证目标抖音视频的匿名 HTTP 解析与完整下载。接入后需在 `parse_video` 的容器重新验收。见 [调研证据](research/douyin-share-http.md)。

## 需求

- R1 继续使用 `POST /api/v1/parse`、`X-API-Key` 和原请求结构。调用方只需提交 `url`，服务端自动识别平台。普通视频下载地址仍位于 `data.videos[0].url`。
- R2 抖音普通视频优先经匿名纯 HTTP 解析，覆盖现有合法短链、视频详情页和移动分享页。响应绑定目标作品 ID，并返回独立客户端可访问的短期 MP4 直链。文件保留平台水印。
- R3 保留抖音静态图文、动态图文错误响应和旧小红书入口。普通抖音视频只有在移动分享页安全、且缺少可用数据或媒体候选时，才可在剩余时限内回退到现有浏览器流程。
- R4 延续现有错误语义、安全限制和资源预算。保留直链签名，遵循日志与验收产物的脱敏规范。缓存到期时间和外部直链到期时间独立。见 `.trellis/spec/backend/service-contract.md:75`、`.trellis/spec/backend/service-contract.md:137`。
- R5 实现、测试、Postman Collection 和部署说明都放在 `parse_video`。沿用本机 Docker `127.0.0.1:8000` 验收。

## 验收标准

- [x] A1 小红书与抖音链接均使用统一入口并进入各自适配器，原鉴权和响应结构通过回归。无效域名返回 `400 INVALID_URL`。对应 R1、R4。
- [x] A2 本机 Docker 中，目标短链以 `refresh: true` 取得 HTTP 200、预期作品 ID 和 MP4 直链，有测试或执行证据证明目标通过纯 HTTP 路径解析。对应 R2、R5。
- [x] A3 Postman 从解析响应取得直链，独立 GET 收到完整 MP4，核对 HTTP 状态、媒体类型、文件头、正文大小和音视频解码。对应 R2、R5。
- [x] A4 浏览器有限回退、抖音图文、旧小红书入口和缓存行为通过回归。作品 ID 不一致、异常 DNS、非白名单跳转、明确登录要求、验证和上游限流得到对应错误。对应 R3、R4。

见 [本机验收记录](verification.md)。

## 首版边界

首版由客户端从 CDN 下载。服务端 MP4 转发、额外下载路由、响应 `platform` 字段、去水印、图文新能力和 VPS 部署属于后续范围。
