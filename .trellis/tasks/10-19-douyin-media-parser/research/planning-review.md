## Findings

已复核主会话最新修改的 `implementation-plan.md`：P0 已拆成 A 状态/ID/错误定位、B 隔离浏览器诊断、C 独立调用方媒体检查与生产 20 秒期限复核；四个仍可访问且属于范围的样本均需成功；有界读取与完整播放已区分。这些主要缺口已解决，不应重复列为待修复项。现有设计保持统一入口、旧入口兼容、共享预算及生产无浏览器方向。以下五项是剩余可执行补充。

### 1. P0-A 的结构摘要增加“扫描完整性”和“目标绑定”证据

依据：`docs/douyin/retry-verification-2026-10-19.md:24` 只确认曾检查 `aweme_id` / `awemeId`，尚无 loader 内层摘要。最新 P0-A 已覆盖字段、类型、包装层，建议再明确诊断输出与停止条件：

- 记录每次扫描是否触及长度、深度、节点上限，以及 JSON 解码是否完整。扫描截断不能归类为“上游未下发目标”。
- 输出 loader key 模板、候选字段路径、值类型和“是否等于目标 ID”的布尔值；动态 key 中的真实 ID 用占位值替换。错误对象仅保留结构与可安全保留的类别，不直接打印原始错误消息或栈。
- 候选是字符串还是整数，须按观察到的 schema 精确处理；拒绝浮点转换、布尔值和精度已损失的 ID。不要为了命中而采用模糊匹配。
- 若只有未知 `id` 字段，要求它与当前路由/作品容器的关联证据，再加入生产识别；不能放宽为任意对象。多个冲突目标候选也应有确定失败结果。

完成条件：最小脱敏 fixture 能证明目标绑定正确、推荐作品不误选、扫描截断与真实缺失可区分。这会直接推进当前未匹配问题，无需继续盲目重试四条链接。

### 2. P0-B 明确浏览器“无账号”与“无已有身份状态”的差别

依据：`retry-verification-2026-10-19.md:45` 与最新 P0-B 已区分诊断/生产；`technical-design.md:47`、`:62` 维持生产不执行脚本、无浏览器。

建议增加：诊断上下文不仅未登录，还应没有既有站点 Cookie、localStorage 与 Service Worker 状态。优先记录初始 HTML、渲染后状态、正常后续网络响应的数据来源关系，避免把已有匿名身份的效果误归因于浏览器引擎。

浏览器能看见内容只证明该诊断上下文可访问；将浏览器生成的 Cookie 移交 HTTP 后成功，也不能证明当前生产无浏览器方案可行。必须在不依赖浏览器状态的既定新匿名 HTTP 会话中复现，才通过当前门槛；否则按已有范围变更流程评审会话获取、签名或浏览器运行方式。

完成条件：诊断报告写清“初始上下文是否干净、数据来自哪里、HTTP 是否独立复现”。不建议导出可用会话、不自动解验证码、不借用用户已有登录配置，也不将诊断操作接入 API 请求链。

### 3. P0-C 增加探测工具的适配边界和格式证据的判定细则

依据：最新 P0-C 已覆盖独立无页面会话读取、格式证据和生产期限，但现有 `scripts/probe.py:19` 固定小红书路由，`:35` 固定小红书白名单，`:38` 固定小红书 Referer，`:51` 只汇总状态、MIME、读取字节数，不能原样作为抖音验收工具。

建议明确未来诊断工具的最小范围：按目标平台选择路由和经过验证的媒体策略；记录最终 host、跳转、状态、读取上限与媒体类型证据；不继承抓取会话 Cookie 或私有 Header。媒体跳转受控校验，即便服务器忽略 Range 返回 200，客户端也按实际字节上限停止读取。

仅有 200、`video/mp4` MIME 或 ISO-BMFF 文件头不能单独证明正确视频内容，尤其不能排除只有音轨的容器。应结合已确认的目标作品/视频 schema 与有限文件证据；如果证据不足，标为未确定，不将抽样读取写成完整播放。候选与元数据必须属于同一目标作品。

完成条件：研究结果区分结构正确、有限读取、完整播放；最多检查代表视频与图片即可，无需下载全部媒体。运行时仍为 `verification=not_checked`，不能把离线成功抽样变成每次响应的保证。

### 4. 静态图文补充坏图、重复槽位及类型冲突的确定规则

依据：`technical-design.md:26` 要求图序，`:31` 排除动态内容；最新 P0-C 已区分同图候选与多张图片，但 P2/P4 尚未明确部分缺图与重复图的行为。公共模型 `app/models.py:104` 的非空集合约束不足以保证图文完整。

建议补入决策表与 fixture：

| 情况 | 建议行为 |
| --- | --- |
| 同一图片槽位有多条 URL | 只选一个允许候选，不输出成多张图。 |
| 不同槽位 URL 相同 | 保留槽位、顺序和数量，不跨槽全局去重。 |
| 已确认普通图文的任一槽位没有可用静态 URL | `MEDIA_NOT_FOUND`；不跳过并重新编号造成部分成功。空图集不能伪装成视频。 |
| `images` 与顶层 `video` 同时存在 | 按观察到的类型/容器语义区分伴奏、占位、封面和真正混合内容，不按字段存在性二选一。 |
| 明确动态标记或不受支持混合内容 | `UNSUPPORTED_CONTENT`；未知结构无法判断时保持 `PARSE_FAILED`，不伪装已识别静态图文。 |
| 正常视频有多个变体 | 固定排序和稳定 tie-break；尺寸、编码、时长等来自选中候选或已验证同作品公共元数据，不跨变体乱借。 |

完成条件：补“中间坏图、跨槽重复图、同槽备用地址、占位 video、动态标记、未知冲突、多视频变体”离线案例；普通图文省略 `live_video`，小红书已有 Live Photo 回归保持独立。

### 5. 接口复用增加平台上下文、序列化与跨入口失败验收

依据：`technical-design.md:15` 已要求保留旧 ID 模型，`:45` 建议适配器返回 `InternalNote`；但现有 `app/models.py:46` 不携带平台，`:142` 的 `ParseSuccess` 绑定小红书 `ParsedNote`，`:160` 的 `to_public_note` 构造旧模型。仅调用原 serializer 会拒绝抖音数字 ID。设计 `:60` 要求新旧文案不同，也要验证共享请求合并的失败路径。

建议明确：

- 新入口使用独立作品/成功 schema，复用媒体和元信息模型；旧入口的 24 位 ID 约束与可选字段序列化保持原样。新入口基于已选平台校验 ID，不能仅凭两种 ID 正则的并集推断平台。
- 平台上下文由调度上下文或内部结果包装明确携带，贯穿缓存、日志和入口序列化；无需增加公开 `platform` 字段。
- 旧入口提交抖音 URL 在网络请求前拒绝。相同小红书结果跨入口共享内部缓存，但分别生成响应元信息；两路均验证 `additionalProperties=false` 和普通图片省略 `live_video`。
- 跨入口共享内部结果/领域错误，不能共享已序列化 HTTP envelope。合并失败时旧入口保留旧文案，新入口使用准确/中性文案，各自有 request_id；覆盖框架校验与网关错误。
- 在已有缓存、配额与取消测试外，补“跨入口请求合并失败”和“一个调用取消、另一调用仍等待”的用例，避免只验成功缓存路径。

完成条件：OpenAPI 的旧路径可观察契约不变，新路径合法表达抖音；平台隔离与入口文案差异不破坏共享预算和生命周期。无需为此重写小红书解析器。
